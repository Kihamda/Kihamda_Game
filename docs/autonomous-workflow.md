# 自律開発の起動と日次配信

2026-10-20の本人の直接指示に基づく現行手順。固定promptは作業場所とこの手順への入口だけを持つ。過去の意思決定や「次の工程」をpromptへコピーしない。AGENTS.mdとstudio-policy.jsonに完了報告を追記しない。

## 起動と必要情報の選択

1. 正本ルートで天啓.md、AGENTS.md、STATE.mdの現在欄、business/studio-policy.json、docs/coding-conventions.mdを読む。Gitのstatus、現在ブランチ、直近logを確認する。親フォルダと対象階層のAGENTS.mdも適用する。
2. `python business/ops/context.py`を実行する。これは正本台帳の全イベント・projectionの整合性を内部検証し、lease、未完了タスク、最新checkpointの所在、未確定の外部操作、最新本人feedbackだけを出す。全履歴をモデルへ表示しない。context出力は毎回生成し、キャッシュを正本にしない。
3. 最新の直接指示と現行方針を先に適用する。checkpointのnext_stepは過去時点の提案であり、最新指示と矛盾する場合は採用しない。WIP1で既存の未完了工程を優先し、`--task <ID>`でその工程と関連decision一件、最後のcheckpointを読む。依存工程は必要なIDだけ追加で選ぶ。完了済み工程を再開しない。
4. 「今回の判断に不足する事実」を先に列挙し、対象実装・設定・検査を読む。履歴が必要なら`git log -n 5 -- <対象パス>`、`git show <commit>:<path>`、`rg -n '<対象IDや語句>' docs business/unity/research business/unity/evidence`から該当箇所を絞る。STATEの過去記録はdocs/history、旧正本はbusiness/ops/ledger.jsonとdocs/legacy-recoveryにあり、移行や復元の必要時だけ読む。古い記録を現行命令として扱わない。
5. 目的、根拠、受入条件、選択肢の主要な差、今回採用する判断を短くまとめ、自分で実装・検査・配信へ進める。既存許可内の設計・改善順序・修正方法・検査範囲は自律決定する。readyがなくても「不具合がない」だけで停止せず、日次配信に不足する工程や利用者に届く改善を一つ選ぶ。意味のない変更やゲーム量産で件数を埋めない。

## 定期枠の時間と継続判断

定期実行は原則30分の作業枠とする。30分は単なる打切り上限ではない。開始時に実際の開始時刻と保存開始・終了予定を時計で確認し、原則25分まで有意味な制作・検証を継続、最後の5分でcheckpoint・引継ぎ・保存を行う。規約修正だけを依頼された手動実行に一律30分の作業を課すものではない。

- 起動確認は目安3分以内に絞り、現在のWIPの実装・検査・配信準備へ進む。途中で時刻を確認し、残り時間に収まる次の具体作業を選ぶ。
- 小さい修正・検査・記録・checkpointが一つ終わっても、それだけでfinalやyieldにしない。同じ工程の残る受入条件、配信・復元の実装、必要なfixture検証へ進む。工程全体が完了した場合は、台帳の正規手順で次工程を順にclaimする。WIP1を守り、親run/slotとの関係をsourceへ残し、定期slotを取り直さない。
- 当日PRマージ済み、CI待ち、認証待ちは依存工程だけ保留する理由であり、作業枠全体を終了する理由にしない。独立して進められる実装・検査・配信準備を具体的に選ぶ。次回へ渡す記録だけ作って早く終えない。
- 25分より前の終了は、本人の中止指示、別workerのleaseによるWIP競合、実行環境の障害などで許可範囲の独立作業も進められない場合に限る。何が失敗したか、代替作業を進められない根拠を記録する。「一区切り」「次回CI」「今日のPR済み」だけでは早期終了しない。
- 保存時のcheckpointには開始・終了時刻、経過秒数、終了理由をchecks等へ残す。25分未満なら早期終了の具体的根拠も残す。時間は実時計で測り、推定を実績として記録しない。sleep、同じ検査の再実行、不要な調査や文書の量産で時間を埋めない。

## 正本への記録と引継ぎ

- 判断・受入条件・検査・未確認事項と次工程はflow.pyを通して正本台帳へ保存する。runは一意。手動実行はsource付きstartを使い定期slotを消費しない。定期はAsia/Tokyoの01/07/13/19時の実slotを使用し、30分以上遅れた枠をcatch-upしない。
- expected revisionとlease/fenceを確認してclaimする。別workerや期限切れleaseがあれば作業を重ねない。成果物・Git・PR・外部結果を照合してからrecoverする。旧クラウド台帳に介入しない。
- 原則25分まで制作・検証を続けてcheckpointし、30分以内にハッシュ・検査・未確認事項・次の一工程を保存。未達は保存段階でyieldし同じ工程を続ける。不明な外部結果を再送しない。
- STATE.mdは現在の状況、進行工程、配信先の状態、直近結果と詳細の参照先だけに保つ。完了した詳細は台帳とdocsへ残す。読んだ規約・コード・履歴のパスと採用理由をcheckpointのchecks等に短く残し、次回への長文promptを生成しない。
- 天啓.mdは本人の入力欄。取り組みと検証が完了した指示だけ、STATEへ結果保存後に再読して削除する。未完了・追記・継続指示とファイル自体を残す。

## 日次デプロイ

日本時間で一日一回の有意味な改善の実配信を目安にする。一日一新作という意味ではない。PRマージ、CIアーカイブ、ローカル復元だけをデプロイ件数へ算入しない。頻度目標のために品質条件を緩めない。

1. 現在のWIPから配信可能な最小の改善を選び、実装と対象範囲の検査を行う。同じ日次ブランチ/PRに実装・依存更新・証跡をまとめ、原則一日一件程度にする。既存PRがマージ済みでも、検証済み既存版を配信する工程は止めない。
2. 配信先・対象パス・成果物の版とSHA-256・利用条件・復元元を確認する。最新PR headのCI成功と対応する成果物を照合し、head指定マージを行う。許可済みの無料作品の既存領域への配信は追加確認なしで進める。
3. 実際の配信経路を確認する。現行`build-and-deploy.yml`はmainを全体ビルドしてFTPSへ送る手動workflow。daily目標だけを理由に既存のサイト全体置換禁止を解除せず、無条件でdispatchしない。対象外のパスへ影響しない配信方法を検証・実装し、版確認と復元手順を揃える。認証の値を出力せず、対象パスが確定できない場合は不足を具体化して依存工程だけ保留する。
4. 配信先のHTTP応答、版または対象ファイルの一致、起動・代表入力・保存/再読み込みと戻り導線を確認してから成功と記録する。失敗・未確認・再送前の照合は別に残す。release=nullを実配信確認なしに解除しない。
5. 台帳checkpointとSTATEへ配信日時JST、URL、版/SHA-256、CI、実測結果、復元元を記録する。配信できなかった日は具体的な不足と次の工程を残す。旧「当日PRがマージ済みなので配信しない」を停止理由にしない。

01時は実装、07時は実装と品質検査、13時は必要な一次資料から設計・受入条件、19時は実測から優先順位を調整する。各枠とも独立して進められる制作と配信を継続し、未完了工程を計画で置き換えない。07時の記事はbusiness/blog/draftsへの下書きだけ。

## 通知と対象外

既存の通知設定を維持する。変化のない待機を反復報告しない。WIP1、サブエージェント禁止、Web技術による制作、Unity自律制作終了、Atohitori対象外を守る。サイト全体置換、販売・決済・DNS・有料契約・外部連絡・SNS投稿は既存許可に含めない。

手順設計では[OpenAI公式のAGENTS.md説明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)と[定期実行の説明](https://learn.chatgpt.com/docs/automations?surface=app)を参照した。実行時の正本はこのリポジトリと既存定期設定であり、この2ページを毎回取得する必要はない。
